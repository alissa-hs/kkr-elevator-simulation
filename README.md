# Elevator Simulation

A discrete-time elevator simulation using **LOOK routing** and **two different dispatch methods**: **nearest** (closest elevator) and **ETA** (earliest estimated arrival).

Each simulation will take passenger requests through a CSV file (template provided). 
Output files will include:
- Elevator positions log
- Passenger summary statistics
- HTML report to provide visuals as well as playback of elevator movements 
- Comparison HTML page that provides a comparison of different dispatch algorithms (nearest vs ETA) on the same input file 

**Required**: Python 3.10+, standard library only (pytest for tests).

## Quick start
```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"

# Run the PDF sample with each dispatcher
.venv/bin/elevator-sim --input examples/sample.csv --elevators 2 --floors 100 --capacity 10
.venv/bin/elevator-sim --input examples/sample.csv --elevators 2 --floors 100 --capacity 10 --dispatcher eta

open output/compare.html          # compare the two runs (macOS; or open the file in any browser)
open output/run_001/report.html   # one run in detail
```

Each run prints where it wrote its files:

```
Wrote output/run_001/positions.csv, output/run_001/passengers.csv, output/run_001/summary.csv, output/run_001/elevators.csv, output/run_001/report.html, output/run_001/run.json
Comparison: output/compare.html
```

`python -m elevator_sim ...` works the same as `elevator-sim ...`. Run the tests with `.venv/bin/pytest`.

## Input

A CSV file with the header `time,id,source,dest`, one row per request:

```csv
time,id,source,dest
0,passenger1,1,51
0,passenger2,1,37
10,passenger3,20,1
```

- `time`: the tick the passenger asks for an elevator (whole number, 0 or more).
- `id`: a unique passenger name.
- `source`, `dest`: floors, numbered from 1. They must differ and be within the building.

Start from [`examples/template.csv`](examples/template.csv) (header only). [`examples/sample.csv`](examples/sample.csv) is the KKR PDF's example inputs and [`examples/busy.csv`](examples/busy.csv) is an office day for a 100-floor building with 10 elevators of capacity 10: 300 people arriving at the lobby (floor 1) in ticks 0–59, 150 trips between floors during the day, and 300 people heading back down to the lobby in ticks 540–599. It is generated by [`examples/generate_busy.py`](examples/generate_busy.py) with a fixed seed; edit the numbers there and re-run it to make your own. Rows can be in any order, spaces around values are ignored, and blank lines are skipped.

| Flag | Required | Meaning |
| --- | --- | --- |
| `--input CSV` | yes | Requests file |
| `--elevators N` | yes | Number of elevators (1 or more) |
| `--floors N` | yes | Floors in the building (2 or more) |
| `--capacity N` | yes | Most passengers one elevator carries at once (1 or more) |
| `--dispatcher {nearest,eta}` | no | Dispatch algorithm (default `nearest`) |

Bad input is rejected before the simulation starts, with every problem listed at once and exit code 2:

```
$ elevator-sim --input examples/sample.csv --elevators 2 --floors 10 --capacity 10
error: line 2: floor 51 is above --floors 10
line 3: floor 37 is above --floors 10
line 4: floor 20 is above --floors 10
use --floors 51 or higher
```

### What counts as bad input

Everything below is checked before the simulation starts. All problems are reported together, each starting with its line number in the file (the header is line 1).

| Check | Example error |
| --- | --- |
| The file exists and can be read | `cannot read nope.csv: ...` |
| The file isn't empty | `file is empty; expected header time,id,source,dest` |
| The header is exactly `time,id,source,dest` | `line 1: header must be time,id,source,dest, got 'time,id,from,to'` |
| Every row has 4 values | `line 5: expected 4 fields, got 3` |
| `time`, `source` and `dest` are whole numbers (no `1.5`, `1e3` or `1_000`) | `line 3: time 'abc' is not a whole number` |
| `id` isn't empty | `line 4: id is empty` |
| `time` isn't negative | `line 2: time -1 is negative` |
| `source` and `dest` are different floors | `line 3: source and dest are both floor 4` |
| Every `id` is unique (each repeat is reported) | `line 4: duplicate id 'c'` |
| Floors are between 1 and `--floors` | `line 2: floor 51 is above --floors 10`, then `use --floors 51 or higher` |
| `--elevators` ≥ 1, `--floors` ≥ 2, `--capacity` ≥ 1, all four required flags given | `error: capacity must be >= 1, got 0` |
| `--dispatcher` is `nearest` or `eta` | `invalid choice: 'fastest'` |

Exit codes: `0` success, `2` bad input or settings, `3` the simulation was stopped by the starvation guard (see [Safety nets](#safety-nets)).

## Output

Every run gets its own folder, `output/run_001/`, `output/run_002/`, ..., so earlier runs are never overwritten.

| File | Contents |
| --- | --- |
| **`positions.csv`** | **Elevator positions log** (required by the PDF): the floor of every elevator at every tick, from 0 to the final tick. |
| **`summary.csv`** | **Passenger summary statistics** (required by the PDF): min, max, mean, median and p95 of wait, travel and total time, plus passenger count, final time, dispatcher and longest-wait passenger. |
| `passengers.csv` | Each passenger's request and outcome: elevator, pickup and dropoff tick, wait, travel and total time. |
| `elevators.csv` | Per elevator: passengers served, moving and idle ticks, stops, peak load. |
| `report.html` | The run on one page: dispatch and routing methods, the statistics, per-elevator table, elevator positions over time, a histogram of total times, an animated playback and every passenger. |
| `run.json` | The input file name, a fingerprint of its requests, and the building settings, used by the comparison page. |

Times are in ticks:

- **wait** = time from request to pickup (mainly impacted by dispatcher algo)
- **travel** = time from pickup to dropoff 
- **total** = time from request to dropoff (wait + travel)
- **p95** = 95% of passengers took this long or less (nearest-rank, so always a real passenger's value)
- **final time** = the tick the last passenger was dropped off

**`output/compare.html`** is rebuilt after every run. It groups runs that had the same passengers (same rows, whatever the file is called) in the same building, so each group differs only in dispatcher, and shows a table (best value per column in bold) and per-passenger dot plots of total time and wait, with mean and p95 marked.

The HTML pages are single files with no external resources.

## Using it from Python (optional)

The command line above is the main way to run the simulation. From Python you can script many runs or work with the results directly:

```python
from elevator_sim import simulate, compute_summary, write_outputs

result = simulate(
    [(0, "passenger1", 1, 51), (0, "passenger2", 1, 37), (10, "passenger3", 20, 1)],
    num_floors=100, num_elevators=2, capacity=10, dispatcher="eta",
)
summary = compute_summary(result)
print(summary.wait.mean, summary.total.p95)   # 14.33..., 62
write_outputs(result)                         # optional: writes output/run_NNN/ like the CLI
```

`simulate()` takes a list of `(time, id, source, dest)` tuples, the same four values as a CSV row, and writes no files by itself.

## How it works

### Each tick

1. **Release:** requests whose `time` has arrived are handed to the dispatcher, which assigns each to one elevator. Assignments are final.
2. **Service:** at each elevator's current floor, riders for this floor get off, the elevator picks its direction (LOOK), then waiting passengers going that way board, oldest first, up to capacity.
3. **Log:** every elevator's floor is recorded in the positions log.
4. **Stop?** If every request has been released and every passenger delivered, the run ends here.
5. **Move:** every non-idle elevator moves one floor.

A RequestStream handles all incoming requests and sends requests at that specific tick, making sure the simulation doesn't peek ahead.

### Routing Algorithm: LOOK

Each elevator keeps moving in its current direction as long as it has a stop ahead: a rider's destination, or a floor where it has been sent to pick someone up. When nothing is left ahead it turns around, and when it has nothing left to do it goes idle. An idle elevator heads for its longest-waiting assigned passenger.

Passengers only board an elevator heading their way. If an elevator going up stops at the floor of someone who wants to go down, they don't get on; it picks them up after it turns around and comes back down.

### Dispatch Algorithms

- **`nearest`:** the elevator closest to the passenger's floor. Ties go to an idle elevator, then the lowest number. It ignores direction, which is its weakness.
- **`eta`:** the elevator estimated to *arrive* soonest heading the passenger's way. For each elevator, the dispatcher counts the floors it would travel on its LOOK route before reaching the passenger:
  - **Idle, or already coming toward the passenger in their direction:** the straight distance.
  - **Moving in the opposite direction to the one the passenger wants:** to the end of its current sweep (its farthest stop), then back to the passenger.
  - **Moving the passenger's way but already past them:** to the end of its current sweep, back to the far end, then to the passenger.

  It uses only what is known at that tick, and ties go to an idle elevator, then the lowest number.

### Safety checks

- **Invariant checks in tests** : after every tick, the tests confirm that no elevator is outside the building or moved more than one floor, no elevator is over capacity, every passenger is in exactly one place with a consistent state, pickup comes after request and dropoff after pickup, riders' destinations are always ahead, and idle elevators are empty. They prove the code is correct; a normal run skips them, so they can't stop your simulation. A failure would mean a bug, not bad input.
- **Starvation guard** (always on): In the worst case scenario, the max ticks a pasenger can go undelivered is about one round trip of the building for every passenger who comes before, plus their own journey, which can be representend by `2 × floors × (passengers + 1)` ticks. If a simulation reaches past this tick, it will exit with exit code `3`. The report shows this limit for each run and how close the run came.

| Scenario | Dispatcher | Wait mean | Wait p95 | Total mean | Total p95 | Final time |
| --- | --- | --- | --- | --- | --- | --- |
| PDF sample (3 passengers) | nearest | 23.67 | 71 | 58.67 | 90 | 100 |
| | **eta** | **14.33** | **43** | **49.33** | **62** | **72** |
| `busy.csv` office day (750 passengers) | nearest | 653.16 | 3076 | 699.58 | 3142 | 3937 |
| | **eta** | **344.96** | **1721** | **391.38** | **1758** | **2571** |
| 200 random scenarios (6,116 passengers) | nearest | 14.89 | 60 | 20.28 | 70 | |
| | **eta** | **12.07** | **49** | **17.46** | **57** | |

ETA roughly halves waits and total times on the office day, but both dispatchers leave a long tail. Neither considers capacity, and assignments are final, so in the morning and evening rushes many lobby-bound passengers are stacked on whichever elevator looks best. That elevator carries 10 per round trip while others sit idle: under ETA, elevator 7 serves 201 passengers and runs until tick 2,570, while most of the rest are idle from around tick 1,000 (passengers served per elevator: 68 / 60 / 68 / 35 / 93 / 42 / 68 / 201 / 68 / 47; under nearest, 35 / 30 / 55 / 71 / 62 / 47 / 43 / 122 / 50 / 235). This is the main motivation for a capacity-aware dispatcher (see [With more time](#with-more-time)).

## Assumptions

- All elevators start at floor 1. 
- An elevator moves one floor per tick, and stops take no time: unloading and boarding happen within the tick.
- A passenger can board on the same tick they ask, if at that tick their elevator is already at their floor and is going (or about to go) in the direction they want to travel.
- Passengers only board an elevator going their direction, and stay with their assigned elevator until delivered.
- Requests at the same tick are handled in file order.
- All three configurable features are required: floors, elevators, capacity.

## Trade-offs

- **ETA ignores capacity.** A full elevator can be assigned a passenger and pass them by until it has room, so the estimate can be optimistic.
- **Assignments are final.** A passenger can't be moved to an elevator that becomes free sooner.
- The starvation limit of `2 × floors × (passengers + 1)` ticks is a reasoned bound, not a proof.
- **Ticks, not seconds.** Results compare dispatchers well, but aren't real-world times.

## With more time

- **Capacity-aware ETA:** penalise full elevators in the estimate, or let a passenger who was passed by be reassigned to another elevator.
- **Stop and door time:** make boarding cost ticks, so ETA would weigh extra stops and the results would be closer to real buildings.
- **Reassignment:** let the dispatcher revisit waiting passengers each tick instead of keeping assignments final.
- **More dispatchers:** destination dispatch (passengers enter their floor in the lobby and are grouped), or zoning elevators by floor range.
- **Traffic patterns:** generators for morning up-peak, lunch and evening down-peak, to compare dispatchers under realistic loads.
